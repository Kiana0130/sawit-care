# Sandbox payment blockers — not ready for use

- Payment grants now have durable, per-payment intervals. Under the per-user database lock, settlement adds 30 days; full or partial refund/chargeback, cancellation, or a provider denial (including Midtrans's documented post-settlement reversal) revokes the unconsumed portion of that grant and shifts later contiguous prepaid time forward without replaying consumed time. Revocations are terminal against stale settlement responses. Partial reversal conservatively revokes the whole remaining grant, not a prorated amount.
- Migration `0005_payment_grants` preserves existing expiry as a separate baseline. Historical payments cannot safely be reconstructed from `granted_until`: reversal of a pre-ledger grant fails with `PAYMENT_LEGACY_GRANT_REVIEW_REQUIRED` and needs manual review. Existing PRO records with no expiry remain subject to the existing no-entitlement rule; an explicit product migration is needed if those records represent indefinite access.
- Payment `granted_until` is the original grant endpoint, not the recalculated current expiry after other grants are reversed. Current entitlement is `users.pro_expires_at`. Grant intervals are mutable current allocations, not a complete event audit trail.
- Status polling and notification reconciliation serialize provider reads on a user lock, but provider responses can still be stale; a mistaken reversal cannot automatically be undone. Payment operations hold a database lock during a network request. A scheduled reconciliation job for missed notifications and operator recovery tooling are not implemented.
- A Snap creation attempt is marked `checkout_uncertain` before contacting Midtrans. `POST /v1/payments/recover` with the original `{"client_id":"<uuid>"}` (authenticated as the owner) performs only a provider status GET, never another Snap POST. It returns the original order and reconciles confirmed status/grants. A status 404 remains `checkout_uncertain` (or `pending` if previously observed), not proof that no checkout exists. Other client IDs are rejected with `PAYMENT_CHECKOUT_UNRESOLVED` while a checkout is created, uncertain or pending; clients should retain and reuse the original ID and inspect payment history if it was lost. Unknown/non-owned IDs return 404. A confirmed terminal provider status permits a new attempt, but stale provider statuses remain a risk and require operational vigilance.
- Recovery cannot reconstruct a lost Snap redirect URL: the Status API does not supply it here. A checkout may exist even when Status returns 404 before payment selection. Preserve its order ID, contact Midtrans/dashboard support and do not make a replacement until the provider confirms the original can no longer be paid. No automated operator resolution is implemented; `created` rows left by a crash before the Snap intent may require retry with the same ID or manual investigation. A GET recovery cannot resolve a permanently unknown or lost unpaid checkout on its own.
- Sandbox end-to-end transactions and webhook delivery have not been verified. Configure a publicly reachable HTTPS notification endpoint and test with sandbox credentials through the deployment environment, without exposing secrets. This implementation makes no production billing-readiness claim.

Midtrans references: [notifications](https://docs.midtrans.com/reference/handle-notifications), [webhooks and Snap 404 behavior](https://docs.midtrans.com/docs/https-notification-webhooks), [GET Status and refund details](https://docs.midtrans.com/docs/get-status-api-requests). A 404 is treated as pending only on owner polling of a known, ungranted checkout; webhook reconciliation still returns an error to permit retry.
